# 学程 UX System

本文是学程后续产品交互的共同约束。Pixso 仍是视觉与组件状态的唯一设计基准；本文只定义信息优先级、操作时机、确认方式和反馈语言，不另行提出视觉方案或新增页面。

## 1. 学程 UX 原则

小程的职责是帮助用户判断和完成下一步，而不是展示系统能力。所有流程遵循以下优先级：

1. **保留上下文**：能在当前卡片或当前对话完成的操作，不跳转到新页面。
2. **一眼可读**：每个屏幕第一眼只突出一件当前最重要的事。
3. **渐进展开**：默认只显示结论和一项主操作；依据、编辑和历史在用户需要时才出现。
4. **相关操作**：只显示与当前状态有关的少量操作，不把所有可能操作同时摆出来。
5. **原位置反馈**：确认、保存、加入日程等结果优先在原卡片更新。
6. **区分决定与结果**：用户尚未决定时展示确认；决定已经完成时展示结果，不重复询问。
7. **降低摩擦**：避免重复输入、重复确认和为了简单动作打开完整页面。
8. **用户掌握决定权**：AI 可提出建议、说明理由和调整建议；长期记忆、正式日程和重要状态必须由用户确认。

### 非目标

- 不把首页做成数据面板、快捷入口集合或 AI 功能目录；
- 不以弹窗替代正常流程；
- 不用后台字段、分数或工程术语要求用户理解系统；
- 不因 AI 推测、普通聊天或一次完成就直接写入长期结论。

## 2. 页面 UX 职责

| 页面 | 用户要完成的事 | 默认只显示 | 允许展开 | 不应承担 |
| --- | --- | --- | --- | --- |
| Splash | 感知品牌已启动 | 品牌与安静的加载状态 | 无 | 首次资料收集、选项、按钮 |
| Onboarding | 给出初始方向 | 一个问题、少量互斥选择、继续/跳过 | 说明为何询问 | 完整资料表单、连续滑屏 |
| Home | 判断现在最值得做什么 | Next Step、下一条日程、路径摘要 | 推荐依据、完整日程/路径 | Dashboard、重复聊天入口 |
| Conversation | 自然表达、协商下一步 | 消息、相关 Inline Action Card、输入栏 | 依据、编辑、历史记录 | 独立的语音/记忆确认页面 |
| Schedule | 查看和确认安排 | 已确认事项、当前待确认建议 | 日期、详情、手动调整 | 把 AI 建议伪装成正式日程 |
| Path | 理解方向和真实进展 | 当前方向、当前阶段、少量证据节点 | 节点依据与历史 | 未确认的目标或能力标签 |
| Profile | 调整陪伴方式与查看个人数据边界 | 资料、陪伴者设置、同步状态 | 记忆管理、来源与删除、系统设置 | 对话中的即时确认 |

## 3. 核心用户 Journey

### 3.1 启动到下一步

```text
Splash
  → 新用户：Onboarding（一次选择或跳过）
  → 已完成引导：Home
  → Next Step（一个主操作）
  → 对话中执行 / 讨论
  → 原位置显示结果与下一步
```

规则：Splash 与 Onboarding 是独立状态，不能作为同一张纵向滑屏内容；已完成引导的用户不能再次被资料收集拦截。

### 3.2 对话中的建议

```text
用户表达
  → 小程提出一个明确建议
  → 聊天内 Inline Action Card
  → 用户确认 / 调整 / 暂不处理
  → 同一卡片显示结果
```

规则：建议不是命令。用户拒绝或暂不处理后，系统不进行羞耻化提示，也不立即用同一说法重复推送。

### 3.3 本地优先与同步

```text
用户在设备上完成操作
  → 本地结果立即可见
  → 用户在“我的”主动选择同步
  → 显示同步中 / 已同步 / 未登录 / 同步失败
```

规则：网络失败时清楚告诉用户“本地内容还在”；不要让后台同步成为用户不可见的行为。

## 4. Home UX

### 信息优先级

1. **Next Step**：做什么、为什么、多久、一个主操作。
2. **下一条日程**：最近一个已确认事项；无事项时给出简短空状态。
3. **学习路径摘要**：当前方向与下一阶段，不展示完整统计表。

### Next Step Card

卡片必须回答：

- **做什么**：一个具体、可开始的小任务；
- **为什么现在做**：一条可理解的推荐依据；
- **大约多久**：可协商的预计时间；
- **下一动作**：唯一视觉主操作，例如“开始学习”。

“和小程讨论”可作为低权重的辅助动作，只有在用户需要协商任务时出现，不能与“开始学习”争夺同等视觉权重。无可靠推荐时，显示“先从一次对话开始”的空状态，不伪造进度、时间或推荐理由。

## 5. Conversation UX

聊天首先是自然交流，其次才是任务、记忆和日程的承载位置。

### Inline Action Card 统一结构

```text
一句自然说明
→ 一项建议或待确认内容
→ 1 个主操作 + 最多 1 个辅助操作
→ 原位置结果
```

不应为了以下简单操作切换页面：接受学习建议、确认一条记忆、把建议加入日程、保存当天记录。

### 对话状态

| 状态 | 用户看到什么 | 允许操作 |
| --- | --- | --- |
| 空对话 | 简短欢迎语，不假装已有上下文 | 输入、从对话开始 |
| 正常消息 | 清晰消息流和必要的卡片 | 输入、相关卡片操作 |
| 生成中 | 与本轮真实发送相关的简短状态 | 等待、继续查看消息 |
| 发送失败 | 原消息保留，说明可重试 | 重试或编辑 |
| 历史恢复 | 真实历史，不插入假欢迎语 | 查看更早消息 |

生成文案不能在用户没有发送内容时说“正在结合你刚才说的话”。

## 6. Memory UX

前台只暴露“是否要记住”和“已记住”的自然语言，不暴露 `memory`、`confidence`、`source_type` 等字段。

### 建议与确认

```text
小程：这个目标会帮助我以后安排学习。要让我记住吗？
[记住] [暂时不用]

确认后：✓ 我记住了
```

- 提议只能出现在相关对话或相关建议旁；
- “暂时不用”是有效选择，不需要额外解释；
- 确认后原卡片更新，不打开管理页；
- Profile 中才提供完整记忆管理：查看、编辑、归档/删除、来源追踪；
- 未经确认的记忆不应被当作长期事实驱动建议。

## 7. Schedule UX

日程区分三个明确状态：

```text
AI 建议 → 用户确认 → 已加入日程
```

### 聊天内建议

```text
明天 19:30 · Python 递归练习 · 30 分钟
[加入日程] [调整]

确认后：✓ 已加入明天日程  [查看日程]
```

### 日程页职责

- 重点显示已确认日程和待确认建议的明显区别；
- “调整”在当前建议附近展开可编辑项，不先弹多层 Modal；
- 手动添加是次要路径，默认收起；
- AI 建议永远不能直接作为已确认日程出现。

## 8. Daily Log UX

成长日志是低输入成本的总结，不是每日大型表单。

```text
用户自然表达当天经历
  → 小程整理为 2–4 条摘要
  → [保存今日记录] [修改]
  → ✓ 今日记录已保存
```

- 摘要在确认前是提议，不能当作稳定结论；
- “修改”优先在当前卡片展开编辑，不跳转到新页面；
- 没有用户输入时不催促填写，也不生成虚构日志。

## 9. Voice UX

语音是 ChatInputBar 的一种输入状态，不是独立功能页面。

```text
长按空输入栏 → 正在聆听 / 上滑取消 → 松手结束
  → 正在识别
  → 文字回填输入栏
  → 用户编辑后自行发送
```

- 聊天上下文保持在原处；
- 录音状态应在输入栏附近、下半屏轻量展开；
- 上滑取消必须有立即的原位置反馈；
- 转写失败说明下一步，不伪造识别结果；
- 原始录音不作为同步数据或成长记忆上传。

## 10. Confirmation / Result 模式

| 场景 | Confirmation（待决定） | Result（已完成） |
| --- | --- | --- |
| 长期记忆 | “要让我记住吗？” | “✓ 我记住了” |
| 日程建议 | “加入日程” / “调整” | “✓ 已加入明天日程” |
| 每日记录 | “保存今日记录” / “修改” | “✓ 今日记录已保存” |
| 学习建议 | “开始学习” / “讨论” | “✓ 已开始；需要时可以继续问我” |
| 同步 | “立即同步” | “✓ 已同步于 14:30” |

同一件事不能在结果出现后又弹出第二次确认。只有不可逆或影响范围较大的操作，例如删除长期资料、覆盖备份，才适合使用 Modal。

## 11. Feedback 层级

1. **Level 1：原位置反馈（默认）**
   卡片按钮、状态标签或行项目直接变成结果。
2. **Level 2：轻量 Banner / Toast（补充）**
   仅在原位置无法解释的跨页面结果、同步失败或后台完成时使用。它不能是唯一反馈。
3. **Level 3：Modal（例外）**
   用于删除、覆盖、授权范围等真正需要集中决定的情形。

## 12. UX Writing 规范

小程的语言应简洁、自然、有判断，但不给控制感。

| 不使用 | 使用 |
| --- | --- |
| “Memory 已成功创建” | “我记住了。” |
| “Learning Evidence 不足” | “目前还不能确定你已经掌握，我们再练一道。” |
| “Context 同步失败” | “刚才没有同步成功，你的本地内容还在。” |
| “你必须完成此任务” | “这一步值得先做；如果现在不合适，我们可以换个安排。” |
| “坚持就是进步” | “这次卡住的地方在递归边界，我们可以只练这一点。” |

写作检查：不假设用户刚说过的话；不夸大掌握；不高频表扬；不机械提醒长期目标；不向用户泄露内部状态名。

## 13. 当前产品 UX 问题清单

以下是对当前 React 运行时与既有本地运行时接线的审计结论，不代表视觉改造建议：

| 优先级 | 当前情况 | 用户影响 | 建议方向 |
| --- | --- | --- | --- |
| P0 | Splash、Onboarding 和应用壳虽然已拆开，但预览与运行时存在双入口，后续改动易让启动状态被误接线 | 新用户可能看到不该出现的重复启动/引导状态 | 以单一启动状态机验收：已完成引导直接 Home，新用户才 Onboarding |
| P0 | Profile 尚未提供独立的记忆管理入口；“长期方向与学习证据”目前进入 Path | 用户无法查看、纠正或删除未来记忆 | 以后在 Profile 增加受控的记忆管理，而不是在对话确认时跳页 |
| P1 | Home 头部“和小程聊聊”与 Next Step 的“讨论”都可进入对话 | 首页有重复聊天入口，Next Step 不够唯一 | 保留任务相关的讨论为辅助操作，弱化或移除泛化聊天入口 |
| P1 | Home 的 Next Step 既有主按钮又有明显辅助按钮，Conversation 还会再次常驻同一任务卡 | 同一建议可能在多个位置抢注意力 | 让 Home 保持唯一焦点；Conversation 仅在相关回合插入任务卡 |
| P1 | 日程页把导入、手动添加、已确认、待确认和 AI 建议同时铺在同一屏 | 主要“确认建议”被多条操作稀释 | 把 AI 建议作为当前最相关的卡片，手动添加保持次级展开 |
| P1 | 当前 AI 建议卡的“确认安排”缺少明确的原位置结果规范 | 用户不易判断建议是否已真正加入日程 | 卡片确认后直接显示已加入和查看日程 |
| P1 | ChatInputBar 已支持长按、取消、识别和回填，但语音状态的反馈层尚未由 UX 规范统一约束 | 容易在实现中变成独立页面或假动画 | 保持输入栏附近、下半屏轻量状态，并只在真实桥接状态变化时展示 |
| P2 | Growth Log / Memory 的前台确认卡还未接入正式对话流程 | 未来可能为了管理数据新建过多页面 | 优先 Inline Action Card + 原位置结果，Profile 只做管理 |
| P2 | 全局运行时可显示 Toast，但没有按成功、失败、跨页面反馈划分层级 | 容易形成所有操作都弹提示 | 后续按本文件的 Level 1–3 使用 |

## 14. 当前流程 → 建议流程

| 场景 | 当前流程 | 建议流程 | 通过标准 |
| --- | --- | --- | --- |
| 启动 | Splash → 预览/运行时分支 → Onboarding 或应用 | Splash → 单一启动判断 → Onboarding 或 Home | 已完成引导不再出现引导；Splash 无业务选项 |
| 首页聊天 | 头部聊天入口 + Next Step 讨论入口 | Next Step 的情境讨论为主；泛化聊天不抢焦点 | 首页一眼只有一个强主操作 |
| 任务建议 | Home 与 Conversation 都可能展示同一任务 | Home 是当前焦点；对话仅在产生建议的回合显示 | 不重复出现同一行动卡 |
| 记忆 | 后台能力规划中，前台无确认体验 | 对话内提议 → 记住/暂时不用 → 原位置结果 | 未确认内容不影响长期判断 |
| 日程 | 建议、确认与其它管理操作同屏 | 聊天/日程内建议 → 加入/调整 → 已加入 | AI 建议与正式日程可一眼区分 |
| 成长日志 | 后台能力规划中，前台无低摩擦确认体验 | 对话总结 → 保存/修改 → 已保存 | 不出现大表单，不自动保存 AI 推断 |
| 语音 | 输入组件已有多状态接线 | 长按 → 聆听/取消 → 转写回填 → 用户发送 | 无独立语音页、无自动发送 |
| 同步 | “我的”中主动触发，运行时提示状态 | 明确显示最近结果，失败说明本地仍在 | 未登录不上传，失败不丢本地内容 |

## 15. 后续开发验收标准

每一项涉及 AI、记忆、日程或成长数据的改动，都应逐项验证：

- 用户是否能在当前上下文完成简单确认；
- 页面第一眼是否仍只有一个主要行动；
- 建议、待确认、已完成是否有明确且不同的状态；
- 失败时是否保留用户输入和本地数据；
- 用户是否能拒绝、修改或暂不处理；
- 是否避免透露内部字段与模型判断分数；
- 是否避免增加不必要 Modal、跳转、重复入口和假反馈；
- 与 Pixso 页面、组件状态和移动端安全区域是否一致。

在这些标准通过前，不应把新的 Memory、成长日志、AI Next Step 或语音能力视为完成。
