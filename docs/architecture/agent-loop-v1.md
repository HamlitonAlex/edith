# 学程 Agent Loop v1 架构决策

## 决策

第一版采用一个主 Agent 和一组纯逻辑内部模块。主 Agent 负责推进 Observe → Diagnose → Decide → Propose → Negotiate → Execute → Verify → Learn；这些模块不作为可独立说话的多个 Agent。

## 方案比较

### 方案 A：一次 LLM 调用生成计划

开发快、表达自然；但状态更新、建议依据、验收和调整难以复现，容易把模板包装成个性化。

### 方案 B：结构化决策内核 + 可替换模型网关

每次行动都能追踪证据、置信度、反方理由和调整记录；模型不可用时也能诚实退化。代价是需要维护状态结构和模块契约，初期代码量更大。

选择方案 B。当前浏览器版本先交付可测试的决策内核；云端模型用于增强语言理解、候选生成和教学表达，但不能绕过验收规则直接把能力标记为“已掌握”。

## 模块边界

- `observer`：把自然语言整理成观察信号，不直接下结论。
- `user-model`：根据带来源的证据更新目标、限制与能力模型。
- `planner`：诊断缺口、比较候选行动，只选择一个下一步。
- `tutor`：一次讲一小块，优先追问思路和提供分层提示。
- `evaluator`：检查理解证据；“点了完成”不等于掌握。
- `memory`：保存系统对用户的认识和决策修订记录。
- `scheduler`：产生早晨、傍晚和晚间的判断机会，不绕过用户权限执行高风险操作。
- `resource-catalog`：保存带来源的候选创作者和资源，按年龄、主题、表达风格与平台筛选；未核验条目不能直接成为推荐。

## “有自己的思想”的工程含义

系统不声称有意识。它通过稳定原则、独立判断、反方理由、置信度和改判条件表现出可检验的主体性。它可以反对用户的即时选择，但必须说明原因、承认不确定性，并保留用户最终决定权。

## 数据边界

Agent Memory 保存对用户的认识、来源和置信度。Obsidian 保存用户知识内容。搜索或回写 Obsidian 需要单独授权，写入前必须确认，二者不合并。

用户提供的资源清单只进入候选层，不等于系统背书。Agent 在推荐某一条具体内容前，必须补齐可访问链接、内容范围和核验状态；截图中辨识不确定的名称也单独标记，不能静默当成准确数据。

## 后续接口

下一阶段增加模型网关、Obsidian 只读索引、系统安全凭据存储、跨端加密同步和主动调度宿主。它们通过接口接入当前内核，不改写决策状态的所有权。
